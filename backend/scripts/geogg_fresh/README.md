# GeoGG Fresh scientific package

The package is installed and executed in the dedicated scientific script-runner
Python environment, not the FastAPI environment.

## Migrated stages

- `stages/s00_inventory.py`: project input inventory, LAS/deviation/checkshot
  inspection, historic reference registration and SEG-Y geometry/QC.
- `stages/s01_well_ties.py`: minimum-curvature trajectories, T-Z table and
  regional-model assessment, velocity QC and synthetic seismic ties.
- `stages/s02_labels.py`: audited petrophysical labels, evidence, QC and task support.
- `stages/s03_extraction.py`: time-bin label aggregation, well/seismic alignment and native-grid patches.
- `stages/s04_features.py` through `stages/s09_inference.py`: feature engineering, model preparation, evaluation and inference.
- `stages/s10_summary.py`: Stage 10 source-volume audit, scientific summary, reports and seismic sections.
- `stages/s11_volume_export.py`: Stage 11 canonical NPY handoff, integrity/QC checks and derived SEG-Y export.
- `stages/s12_geobody.py`: Stage 12 exploratory geobody extraction, mesh/SEG-Y exports, figures and read-only API assets.

Stages 10–12 now follow the same source layout as their output directories:
`stages/s10_summary.py` → `stages/10_summary/`,
`stages/s11_volume_export.py` → `stages/11_volume_export/`, and
`stages/s12_geobody.py` → `stages/12_geobody/`. The top-level
`process_geogg_*.py` files are backend worker entry points only.

Run stages 00–07 through `scripts/process_A_foundations.py`, Stage 08–09
through `scripts/process_B_inference.py`, Stage 10–11 through
`scripts/process_C_volume_products.py`, and Stage 12 through
`scripts/process_D_geobody.py`. Each operation remains in its existing
APGCE processing job; upstream jobs are read-only inputs where configured.

## Configuration

The backend ships `scripts/A_foundations.yaml`, which is synchronised to
`site_data/scripts/A_foundations.yaml` and used automatically. It provides safe
scientific defaults without hard-coded dataset paths or dataset UIDs. Override
it with `APGCE_GEOGG_CONFIG` or `--config` when required. The active processing
job directory is supplied by APGCE and overrides `project.output_root` at runtime.
The existing APGCE runner supplies `--input-manifest`; the wrapper forwards it to
`APGCE_INPUT_MANIFEST`, which the shared `StageContext` reads. For manual runs,
that environment variable may be set directly instead. The manifest remains
optional at the runner interface, but Stage 00 will report BLOCKED when no
registered dataset inputs are supplied.

## Dependencies

Install `requirements-science.txt` in the dedicated local/SLURM runner
environment. Install CUDA/PyTorch separately with a build compatible with the
HPC nodes. Do not install these dependencies into the FastAPI environment.

The migrated stages reuse the existing APGCE processing job and storage
infrastructure. `APGCE_JOB_ID` is the authoritative GeoGG run ID and matches the
UUID in `site_data/processing_jobs/<job-uuid>/`. Outputs are stored beneath that
job directory, so result polling, logs, metadata, dataset inputs and evidence
remain associated with the same processing record. Each APGCE processing entry point (Stages A–F, including the Stage 12
Geobody worker) uses the shared `scripts/scripts_utils.py`
`@validate_outputs` decorator. The worker decorator validates the required
job-level outputs and owns the standard `result.json`; stage-specific summary
files retain detailed processing and provenance information. Stage artifacts and provenance are stored directly under the processing-job
directory in `stages/` and `provenance/`.


## Stage 00 inventory authority

Stage 00 does not scan configured directories or create dataset identities. Its only
input inventory is `APGCE_INPUT_MANIFEST`, generated by the APGCE backend from selected
dataset records. `dataset_id` is the authoritative UID. The backend also supplies
`well_id`/`well_name` and `survey_id`/`survey_name` associations where registered.

Well logs, deviation surveys and checkshots are grouped by their registered well
association. Seismic volume roles are read from dataset metadata (`geogg_volume` or
`geogg_role`) or an explicit `dataset_roles.seismic.<volume>` UID mapping in the
editable config. A well-header workbook can be selected with
`dataset_roles.well_header`. These role mappings select existing backend records;
they do not create a parallel registry. Unselected or unassociated files are never
discovered by filesystem scanning.


## Foundations outputs

The combined foundations worker runs Stage 00 and then Stage 01 in one APGCE
processing job. The standard job result is written by `scripts_utils.validate_outputs`;
`geogg_foundations_summary.json` records the GeoGG run ID and per-stage status.
Detailed artifacts are grouped under:

`stages/00_inventory/` and
`stages/01_well_ties/`

Stage 00 produces inventory/QC tables (`well_availability.csv`,
`log_curve_inventory.csv`, `seismic_volume_inventory.csv`,
`stack_consistency_check.csv`, `fluid_indicator_screening.csv`,
`historic_reference_inventory.csv`, `seismic_registration_check.csv`), a
`data_manifest.json`, `config_snapshot.yaml`, and coverage/location figures.
Some rows and tables are conditional on the selected registered inputs.

Stage 01 produces trajectory and T-Z/QC tables (`trajectory_summary.csv`,
`trajectory_stations_all_wells.csv` when stations are available,
`tdr_table_qc.csv` when checkshots are supplied, `regional_model_selection.csv`,
`lowo_validation.csv`, `historic_polynomial_inspection.csv`,
`polynomial_coefficients_used.csv`, `tz_samples_all_wells.csv` when samples are
available, `velocity_qc.csv`, `tie_events.csv`, and `tie_summary.csv`) plus
per-well and all-well T-Z/velocity/synthetic-tie figures. Exact optional outputs
depend on the registered inputs and configuration; stage provenance records
the outputs actually produced.

## Model releases (v82)

When stages 00–07 complete successfully and Stage 07 has at least one successful
final model, the runner creates an immutable release under
`site_data/model_releases/<release-id>/` (the same backend-managed storage root
that contains `processing_jobs/`). The release ID is `geogg-<processing-job-id>`.

A release contains final model files, the Stage 05 feature schema and training
manifest, the Stage 06 feature-set and fitted-transform JSON files, the Stage 07
model registry, sealed outer-test predictions, fit audit and architecture
metadata, plus Stage 03 extraction/patch contracts. It records checksums for
copied files and the source processing-job ID in `manifest.json`. The potentially
large Stage 03 training patch array is intentionally not duplicated: inference
must extract compatible patches from its selected input datasets using the
recorded patch contract.

Release creation is atomic. Existing release IDs are never overwritten. A run
with no successful final model does not create an empty release. Missing required
artifacts or integrity-check failures fail the training worker rather than
registering an incomplete release. The source processing job remains unchanged.

This update establishes packaging only. It does not yet change Stages 08–13 to
load a release; registry APIs and inference-job decoupling are subsequent work.
